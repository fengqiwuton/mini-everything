# v0.3 重扫性能与验证

2026-10-04，本机 Windows、MinGW-w64 GCC 14.2、Release、SQLite 3.53.4。v0.3 采用扫描连接局部的缓存目标 64 MiB；提供 `--db-cache-mib 1..1024`，保持 schema 1 和事务/外键/日志/同步/溢出策略。

## 数据库副本实验

用户 v0.2 全量重扫为 108983 ms，其中 prepare 38726.11 ms、metadata 36238.13 ms、write 27059.99 ms、commit 3295.57 ms。本次开发没有重新遍历该真实目录。

使用只读源连接，通过 SQLite backup 创建独立副本。源索引为 305995776 字节、769395 节点、一个根目录。每个副本只执行本根旧节点删除，随后提交，检查外键和完整性；原索引未写入，路径与文件名未发布。以下为一轮测量，不是整次扫描或多轮中位数。

| 缓存目标 | 旧节点删除 | 提交 | 两者合计 | 删除期间缓存未命中 | 删除期间脏页溢出 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 默认（2000 KiB，约 2 MiB） | 38606.40 ms | 3151.52 ms | 41757.92 ms | 413844 | 347169 |
| 64 MiB | 22122.30 ms | 6208.89 ms | 28331.19 ms | 89391 | 69323 |
| 128 MiB | 17730.50 ms | 6566.49 ms | 24296.99 ms | 78181 | 41499 |

64 MiB 的删除加提交约减少 32.2%。删除耗时与用户原先的 prepare 接近，而增加缓存显著减少脏页溢出，支持缓存不足是该数据库清理成本的重要来源。提交耗时上升，因此不能单用删除阶段的下降比例预测整次扫描。CPU、磁盘和系统负载仍可能影响结果。

数据库实验复现方法：对单根、schema 1 索引用只读 SQLite backup 制作三个新副本；分别设置 `PRAGMA cache_size=-2000/-65536/-131072`，保留 foreign_keys=ON、trusted_schema=OFF 与原来的日志/同步策略。计时执行 `BEGIN IMMEDIATE; DELETE FROM nodes WHERE root_id=?; COMMIT;`，分别记录删除和提交；删除前后读取 SQLITE_DBSTATUS_CACHE_MISS / CACHE_WRITE / CACHE_SPILL，最后执行 integrity_check 和 foreign_key_check。副本生成、校验耗时不计入表中。

## 受控完整扫描与重扫

使用与 v0.2 报告相同、保持不变的受控目录，共 10000 文件、101 目录。v0.2.0 归档程序与 v0.3 Release 交替运行三轮，每个版本每轮先新建索引，再重扫同一索引；名称、路径、类型、大小、修改时间、扩展名、父路径及根归属逐条一致，完整性、外键及格式标识检查通过。

| 阶段 | v0.2 三轮 | v0.3 三轮 | v0.2 中位数 | v0.3 中位数 |
| --- | --- | --- | ---: | ---: |
| 新建 | 187 / 195 / 218 ms | 196 / 229 / 179 ms | 195 ms | 196 ms |
| 重扫 | 371 / 562 / 455 ms | 348 / 354 / 368 ms | 455 ms | 354 ms |

这是补强内容校验后的最后三轮：重扫中位数约减少 22.2%，新建索引基本不变；先前一组三轮重扫为 472 ms → 406 ms，约减少 14.0%。存在明显轮间波动，不能只取最快一次。该目录只有约 4.4 MB 数据库，64 MiB 缓存的收益不能代表 306 MB 索引，也不能预测 76 万条记录的实际重扫耗时。缓存可能已预热，进程启动和校验不计入上述 CLI 内部耗时。

## 复现与诊断

```powershell
python scripts/benchmark.py --baseline <v0.2.exe> --candidate <v0.3.exe> --baseline-profile --root <固定测试目录> --output-dir build/benchmark-v0.3 --mode both --rounds 3
```

`--mode fresh` 保持原来的新建索引测量；`--mode rescan` 用基线程序生成种子数据库，再测两个版本重扫，种子时间不计入结果；`--mode both` 分别记录新建和重扫。可通过 `--candidate-cache-mib 128` 测量其他缓存目标。JSON 的 `median_internal_ms` 和 `speedup_by_phase` 按阶段分组，避免混合两类耗时。

v0.3 把 prepare 拆分为 open、transaction、schema、roots、clear、statements，报告从连接打开到提交后的 SQLite cache 统计。内存按需分配，MiB 数值是页缓存近似目标，而非整个进程的内存硬上限；参见 [SQLite cache_size](https://www.sqlite.org/pragma.html#pragma_cache_size) 与 [cache_spill](https://www.sqlite.org/pragma.html#pragma_cache_spill)。

本机 Debug 和 Release 各 26/26 测试通过，新增缓存参数与范围、连接局部设置、外键/同步策略、prepare 子阶段、多根目录成功重扫和失败回滚。远程结果见 [GitHub Actions](https://github.com/fengqiwuton/mini-everything/actions)。

v0.3 对 v0.2 种子索引的重扫通过；v0.1、v0.2、v0.3 查询同批 10000 文件结果完全一致。独立审查无 P1/P2；已补强扩展名和根归属校验，并使用带中文名称的缓存策略测试。受控注入错误扩展名或根路径时，旧基准漏检，新基准均拒绝错误结果。
