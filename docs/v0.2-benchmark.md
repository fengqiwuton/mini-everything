# v0.2 扫描性能与验证

2026-10-04，本机 Windows、MinGW-w64 GCC 14.2、Ninja、CMake 3.31.5，Release 编译。基线为 v0.1.0 的扫描代码，候选为 v0.2 原生 Windows 扫描实现。SQLite 版本和 schema 1 保持不变。

使用同一棵不变的受控临时目录：100 个子目录，每个 100 个文件，加上根目录，共 10000 文件、101 目录。两个版本交替运行三轮，每次创建不同的数据库；未运行用户真实目录的大规模扫描。

| 版本 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 中位数 |
| --- | ---: | ---: | ---: | ---: |
| v0.1 | 3290 ms | 3366 ms | 3533 ms | 3366 ms |
| v0.2 | 232 ms | 240 ms | 227 ms | 232 ms |

表中使用 CLI 报告的扫描耗时，中位数比约 **14.5 倍**。包含进程启动的墙钟中位数分别为 3416.91 ms 和 286.61 ms，比约 11.9 倍。此前的一组三轮测量为 2753 ms → 193 ms，方向一致。缓存可能已预热，磁盘、杀毒软件和系统负载没有隔离；这不是对用户 76 万条记录扫描耗时的预测。

每轮逐条比较名称、完整路径、文件/目录类型、大小、修改时间及父节点路径，结果完全一致；数据库完整性和外键检查通过。ID 不要求一致。跨版本搜索同一批 10000 条文件结果一致，v0.2 可读取 v0.1 数据库，v0.1 可读取 v0.2 数据库。

v0.2 第一轮诊断：prepare 2.38 ms、metadata 44.11 ms、identity 0.18 ms、write 124.11 ms、commit 52.06 ms，逐文件身份检查 0 次。本地单链接场景省去了重复的数据库身份打开；文件大小和修改时间直接来自原生目录枚举。没有关闭数据库事务或删除安全检查。网络路径和数据库有额外硬链接时执行保守的逐文件检查。

## 复现

准备一棵固定的测试目录，并分别构建 v0.1.0 与 v0.2.0 Release 可执行文件，将数据库输出放在测试目录外。Python 3 标准库即可运行：

```powershell
python scripts/benchmark.py --baseline <v0.1.exe> --candidate <v0.2.exe> --root <固定测试目录> --output-dir build/benchmark --rounds 3
```

脚本交替执行两个版本，验证索引内容和数据库完整性，并生成 `comparison.json`。本机数据库、文件路径和原始测评文件保留在忽略的 `build/` 下，不提交。报告仅包含统计数据。

## 正确性与审查

本机 Debug、Release 各 22/22 个 CTest 用例通过，覆盖扩展路径、超过 260 字符的深层目录、中文、链接跳过、数据库硬链接、目录读取失败回滚、SQL 失败回滚、盘符根目录包含关系、UNC/本地数据库别名和 CLI 诊断。UNC 管理共享用例在共享不可用的主机上可跳过，本机实际运行通过。

独立子 agent 审查发现的盘符根目录与 UNC 别名问题均先通过回归测试复现，再修复；定向复核无新的 P1/P2 问题。远程 MSVC 和 Linux 验证结果可查看 [GitHub Actions](https://github.com/fengqiwuton/mini-everything/actions)。
